   Corrections to what was assumed below, found while building it:
   - the omitted constraint is NOT S[j] <= S[j-1]. That only forces the levels
     to be non-increasing, and the solver evades it by draining all 16 segments
     UNIFORMLY, which still bills the cheap bottom ones. Measured: $1.07 booked
     against $1.99 of real degradation on a full-pack discharge. The constraint
     actually needed is a STAIRCASE — a segment may hold energy only if the one
     below it is full — which needs a binary per segment per interval:
         stored[s] <= cap[s]*inUse[s];  stored[s-1] >= cap[s-1]*inUse[s]
     So step 1 is a MILP whether or not Q^CAL is included. Adding the implied
     stored[s] <= stored[s-1] and inUse[s] <= inUse[s-1] as explicit cuts is
     what makes it tractable at all.
   - simultaneous charge+discharge was checked for and does NOT occur, so no
     exclusivity binaries were added. There is a test guarding this.
   - CBC cannot cope: it stalled past 90s on 96 intervals. highspy added to
     flake.nix; lp.defaultSolver() prefers HiGHS, falls back to CBC.
     HiGHS keeps its default 0.01% MIP gap — deliberate, immaterial next to the
     degradation model's own error, and closing it costs most of the runtime.

   DONE — discrete power mode, which is what makes the bound FAIR.
     The agent has three actions, so it moves the rated throughput or nothing.
     An unrestricted oracle picks any power and books money the agent physically
     cannot earn, so a gap against it mixes bad policy with an unreachable power
     setting. solve(discretePower=True) restricts every interval to the same
     three choices, with a partial top-up allowed only where physics forces one.
     Four binaries per interval; see _discretePower for why atFull/atEmpty
     cannot be relaxed to continuous.
     Measured on SA1 2024-01-10, 288 intervals, no Q^CAL:
       continuous, default gap   25.8s   profit 21.9515
       discrete, proven optimal 1554.9s  profit 21.8041
       discrete, 0.5% gap         81.8s  profit 21.7269, dual bound 21.8353
     So roughly 15 cents a day of the continuous oracle was never reachable.

   DONE — quote Schedule.dualBound, never Schedule.profit, as the bound.
     A gap-limited or time-limited solve returns an incumbent that can sit BELOW
     the true optimum, and a bound that is too low understates the agent's
     shortfall and flatters it. The dual bound stays valid either way, which is
     what makes a relaxed gap affordable at all. HiGHS minimises internally, so
     pulp negates a maximisation and the raw mip_dual_bound arrives with the
     opposite sign; _solverInfo flips it.

   DONE — chunking, in rl/baseline.py. One window is one episode, every window
     starts from the same fixed SoC, no window sees past its own last interval.
     Independent, therefore cacheable and parallel. Cached under data_cache/,
     keyed on every input that changes the answer.

   TODO — remaining cost problems in this step
   - ALWAYS pass threads=1 when solving windows in parallel. HiGHS otherwise
     takes every core in every worker and the oversubscription costs an order of
     magnitude: four unrestricted workers ran at about 8 minutes a window
     against 44 seconds for one solve alone. buildBaseline sets it when
     workers > 1.
   - solve cost is strongly DAY-DEPENDENT, which one sample hides. Continuous
     with Q^CAL took 44s on 2024-01-10 but 187s on 2024-01-01 at a 2% gap. Do
     not size a batch from a single day.
   - single-threaded throughput is about 5.4 windows/min on 6 workers for the
     continuous no-Q^CAL solve, and memory caps the worker count at 6 on 16GB
     (480MB a worker without Q^CAL, 600-790MB with it).
   - the discrete bound over a whole year is still unaffordable: 365 windows at
     the 300s time limit is about 10 core-hours. The 2025 test bound currently
     falls back to a continuous no-Q^CAL solve, which is DOUBLY LOOSE but still
     a valid upper bound, because it has powers the agent lacks and ignores a
     cost the agent pays. Tightening this is the main open item.

   - DECIDED: the chunk length IS the RL episode horizon H (step 2). Not a
     solver tuning knob — a property of the comparison. An oracle that solves a
     whole year at once has strictly more foresight than the agent can ever
     exploit, so its $ figure is not the bound the agent is being measured
     against. Pin H once, in the shared config from step 0, and have both the
     oracle and the env read it.
   - this KILLS the overlapping-window idea that used to be written here.
     Lookahead past the boundary exists to stop the solver dumping energy it
     cannot value at the chunk's last interval — but if the agent also cannot
     see past the episode end, that dumping is SHARED behaviour, not oracle
     bias. Adding lookahead would hand the oracle information the agent does
     not have and inflate the bound. Also saves the 2x work.
   - matching the LENGTH is not sufficient. Both boundary conditions must
     match too, or the bound is still wrong:
       (a) starting SoC — either both carry the previous chunk's/episode's
           final SoC forward, or both reset to the same fixed value. Carrying
           forward makes chunks SEQUENTIAL (no parallelising); resetting makes
           them independent and therefore parallelisable, at some cost in
           optimality. This is the real reason to pick one.
       (b) terminal SoC — if the env gives the agent any end-of-episode
           terminal value on leftover energy, the LP needs the same term in
           its objective. If neither does, both dump; that is consistent.
   - so chunking is BLOCKED on step 2 pinning H and the reset rule. Do not
     pick a chunk size on solver-speed grounds alone. If H turns out to be
     long enough that a chunk is intractable, that is a constraint on the
     episode design, not something to paper over in the LP.
   - keep a separate whole-horizon "unbounded foresight" number if one is
     wanted for the writeup, but label it as NOT the agent's bound.
   - MIP time grows superlinearly in the number of binaries, so total time =
     chunks x time-per-chunk gets worse as chunks get bigger. Relevant only as
     a cost estimate for a given H now, not as a way to choose H.
   - to keep the honesty check meaningful after stitching, have solve() return
     degradation PER INTERVAL from the LP's own objective terms, and sum it —
     do not rescore the stitched SoC path with schade.py, or the test that
     compares the two becomes tautological.

2) RL environment — CORE DONE, in rl/
   - H = 288 and SoC resets to 0.5, both in config.py and read by the env and
     the oracle chunking alike.
   - rl/env.py: BessEnv, 3 discrete actions (charge / idle / discharge) at the
     rated throughput. No C-rate taper in the Schade model, so SoC affects only
     feasibility, not the rate. A full step is ASYMMETRIC in SoC: charging adds
     nu_C * E, discharging removes E / nu_D, which is +4.75% against -5.263% for
     the paper battery. Getting either efficiency on the wrong side is a silent
     5% drift away from the oracle.
   - boundary rule: mask an action only at zero headroom, otherwise clip to the
     headroom. The discrete LP permits exactly the same partial top-up, so the
     two stay matched. MaskablePPO reads the mask; DQN and A2C cannot be masked,
     so clipping is their only protection, which is consistent because the
     discrete LP also permits a zero-energy charge into a full pack.
   - rl/features.py owns the observation and is the single definition of it.
     64 slots: SoC, 12 five-minute prices, 46 half-hour bucket means, hour and
     season sine-cosine pairs, intervals remaining. (288-12)/6 = 46 exactly, so
     the layout closes with no ragged bucket.
     Two slots are there for bound integrity, not richness. Intervals remaining
     is required because the episode is finite-horizon and both sides dump at
     the boundary; without it the observation is not Markov and measured regret
     would be inflated by a modelling artefact. And the tail is PADDED, never
     filled by reading past the episode, which would hand the agent foresight
     the oracle lacks and let it beat its own bound.
   - reward: per-interval profit minus the oracle's per-interval profit. The
     baseline depends only on (window, interval), never on the agent, so it
     cannot change which policy is best. It therefore does NOT have to share the
     battery model it centres, which is why the training baseline can use the
     cheap no-Q^CAL solve while the env keeps Q^CAL on.
     gamma MUST stay 1.0. Under discounting the subtraction stops being a
     constant shift and reweights the oracle's own spike-shaped profit profile
     into the agent's incentives.
   - rl/algos.py: --algo over MaskablePPO, DQN, A2C. config.algorithms lists the
     names so the CLI can offer them without importing torch.
   - 5 seeds, mean +/- SD, in rl/evaluate.py.
   - THE test that everything rests on: rl/test_env.py::TestMatchesTheOracle
     replays the oracle's own schedule through the env and holds the SoC path
     and the degradation to 1e-9. If that ever fails, nothing downstream is
     worth measuring.

 degradation model (Gap 4) — DONE, in degradation/schade.py. Schade &
 Egging-Bratseth (2024), doi:10.1002/est2.588. Q^CD (Eqs. 1, 2, 11) is
 implemented and verified against the paper's Figure 3 money target.
 Remaining: Q^CAL (Eq. 27, one np.interp line), then Eq. 10 to convert to $.

 This is NOT post-hoc rainflow. It is the causal piecewise-linear surrogate
 for it, which is why it works as a per-step reward AND as an LP objective.
 So there is no v1/v2 split any more and no "oracle only bounds v1" caveat —
 one agent, one objective, bounded exactly. Keep a post-hoc rainflow scorer
 for reporting only; never feed it back as reward (double-counts vs Eq. 11).
